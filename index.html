단계

  1. 브라우저는 web-app(Next.js 16)과만 통신합니다. Next.js rewrite가 /api/order/*를 core-api로, /api/file/*를 file-api로 보내며, 운영에서는 파일 요청을 파일 서버의 자체 도메인으로 직접 보낼 수 있고 그 서버는 credentials를 허용하는 CORS 허용 목록으로 응답합니다.
  2. core-api와 file-api는 같은 로그인을 공유합니다. 둘 다 같은 Redis 저장소와 key prefix를 쓰는 express-session을 사용하고, 같은 MySQL 스키마를 읽고 씁니다.
  3. 외부 exe와 기존 클라이언트가 쓰는 레거시 라우트는 경로와 응답을 그대로 두고, 바뀐 동작은 새 라우트로 추가합니다. 예를 들어 POST /v1/orders/:code/state는 예상한 현재 상태를 함께 받아 그사이 바뀌었으면 409를 반환하고, 기존 GET 라우트는 그대로 남습니다.
  4. file-api는 Python AI(nnU-Net 분할, STL 출력)를 python-shell 자식 프로세스로 실행하며, 작업은 DB 테이블(gpu_slot)에서 GPU 슬롯을 임대하는 대기열에서 가져옵니다. 45분을 넘기거나 취소되면 프로세스 트리 전체를 종료합니다.
  5. S3 쓰기 · 삭제는 먼저 storage_outbox에 파일 경로당 한 행으로 기록되고, 워커가 10초에서 최대 1시간까지 늘어나는 간격으로 재시도하며 보냅니다. DB가 내려가 있으면 작업을 메모리에 보관했다가 DB가 돌아오면 테이블에 기록합니다.
  6. 스키마 변경은 번호가 붙은 SQL 파일로 하며, 러너가 각 파일을 한 번만 적용하고 sha256 체크섬을 schema_migrations에 저장합니다. 체크섬이 다르면 중단하고, 명시적으로 허용하지 않으면 로컬이 아닌 호스트에는 적용하지 않습니다.

왜 이렇게 했나

외부 exe와 아직 운영 중인 레거시 앱이 같은 API 계약과 테이블을 쓰고 exe는 팀이 바꿀 수 없으므로, 한 번에 전환하는 방식 대신 같은 계약 뒤에서 라우트 단위로 다시 구현했습니다. 같은 이유로 스키마는 새로 설계하지 않고 테이블 · 컬럼 · 인덱스를 추가하는 방식으로만 바꿉니다.

Q&A

Q. 의사가 파일을 올리는 중에 S3에 접속할 수 없으면 어떻게 됩니까?
파일은 사내 서버 디스크에 남고, S3 작업은 storage_outbox의 행으로 남아 워커가 최대 1시간까지 늘어나는 간격으로 재시도합니다. DB까지 내려가 있으면 작업을 메모리에 보관했다가 나중에 테이블에 기록합니다. 디스크 사본은 S3에 같은 내용(MD5 또는 SHA-1)이 있는 것이 확인된 뒤에만 정리됩니다.
Q. 외부 exe가 쓰는 엔드포인트의 동작을 바꿔야 하면 어떻게 합니까?
그 엔드포인트는 바꾸지 않고 경로와 응답을 바이트 단위로 유지합니다. 새 동작은 별도 라우트(예: /v1/orders/:code/state)로 만들어 웹 앱이 그쪽으로 옮겨 가고, 레거시 라우트는 외부 호출 범위가 확인될 때까지 그대로 둡니다.

Steps

  1. The browser talks only to web-app (Next.js 16). Next.js rewrites map /api/order/* to core-api and /api/file/* to file-api; for production the file client can call the file server's own domain directly, which answers with a credentialed CORS allow-list.
  2. core-api and file-api share one login: both use express-session with the same Redis store and key prefix. Both read and write the same MySQL schema.
  3. Legacy routes used by the external exe and old clients keep their path and response, and changed behaviour is added as a new route. For example POST /v1/orders/:code/state takes the expected current state and returns 409 if it changed meanwhile, while the old GET route stays as it was.
  4. file-api runs the Python AI (nnU-Net segmentation, STL export) as a python-shell child process, taking jobs from a queue that leases GPU slots from a DB table (gpu_slot). A run past 45 minutes, or a cancel, kills the whole process tree.
  5. Every S3 write or delete is first recorded in storage_outbox (one row per file path), and a worker sends it with retries spaced from 10 s up to 1 h. If the database is down, the jobs are held in memory and written to the table when it is back.
  6. Schema changes are numbered SQL files: the runner applies each once and stores its sha256 checksum in schema_migrations. It stops on a checksum mismatch and refuses a non-local host unless that is explicitly allowed.

Why this way

The external exe and the still-running legacy apps use the same API contract and tables, and the exe is outside the team's control, so a one-time switch was rejected in favour of rebuilding route by route behind the same contract. For the same reason the schema only grows (new tables, columns and indexes) instead of being redesigned.

Q&A

Q. What happens if S3 is unreachable while a doctor uploads files?
The file stays on the on-prem disk and the S3 job stays as a row in storage_outbox; the worker retries it with growing pauses of up to one hour. If the database is also down, the jobs are held in memory and flushed to the table later. The disk copy is evicted only after S3 is confirmed to hold the same content (MD5 or SHA-1).
Q. How do you change the behaviour of an endpoint the external exe depends on?
We do not change it: its path and response stay byte-identical. The new behaviour is a separate route (for example /v1/orders/:code/state), the web app moves to it, and the legacy route stays for outside callers until their use is confirmed.

Steps

  1. The Next.js proxy checks only that a session cookie exists on signed-in routes. Without one it redirects with 307 to /login?next=…, or to the session restore endpoint when a remember-me cookie is present.
  2. The server layout resolves the user with getCurrentUser(), wrapped in React cache, so layout and page share one /me call. An invalid session is a server redirect, and the user is passed to AuthProvider as initial state.
  3. On a cold browser the page prefetches into a request-scoped QueryClient with retry: false and renders inside HydrationBoundary, so the rows are in the first HTML. The layout uses its own client because layouts and pages render in parallel, and a failed prefetch leaves the query to the browser.
  4. The client persists only allow-listed query keys to sessionStorage (12 h max age, a buster per user index) and sets a warm_cache cookie; with that cookie the server skips prefetch and sends lighter HTML. Logout, login and any 401 clear the cache, the ETags, the snapshots and the cookie.
  5. An inline script in the server HTML puts the last saved DOM snapshot back while the page is still parsing. The last tap made on it is replayed when the live view is ready, only if exactly one matching element exists within 3 s.
  6. Queries use getWithEtag: If-None-Match is sent only when a cached copy exists, and a 304 returns that same object, so structural sharing causes no re-render. For the member list and order detail the server decides the 304 from one small version query (counts, MAX(updated_at), CRC32 of the shown columns); the staff list hashes its full result.

Why this way

The first HTML must be complete (rows visible even with JavaScript off), so loading.tsx streaming was rejected: it sends a shell and skeleton and fills the content in later. revalidatePath after writes was also rejected, because re-rendering layout and page would cost four API calls per mutation while TanStack Query already owns the client cache.

Q&A

Q. Could the restored snapshot or cache show data that changed meanwhile?
Only for a moment: the snapshot is replaced as soon as the live view is ready, and after a restore the provider invalidates every persisted query once, so each is re-checked with If-None-Match. Changed data comes back as 200 with a new ETag and replaces the old copy; unchanged data comes back as 304.
Q. Does the 304 path work with two core-api servers behind a load balancer, and what does a 304 still cost?
Yes: the ETag is a sha256 over DB-derived version values, and the dictionary version is a hash of its content instead of a per-process counter, so two servers with the same data give the same ETag (a test failed with 3 vs 2 before that change). A 304 still runs one small aggregate query per request, but skips the full query and the JSON body.

Steps

  1. On submit, file-api opens one transaction, upserts the day's row in daily_seq (prefix = KST date, with a separate prefix for the Partner A company group) and locks it with SELECT … FOR UPDATE. The next number is max(last_value, the largest number already in order for that date, legacy-written codes included) + 1.
  2. Under that lock it checks submit_keys for the draft, locks the draft and its finished gpu_job rows, inserts order, order_files, scans and submit_keys (draft_id primary key, order_id unique), stores the counter and renames the draft folder to the order folder. UNIQUE(order_no) makes a duplicate code an insert error instead of a silent second order.
  3. If anything fails, the folder is renamed back and MySQL rolls back the rows, and errno 1062, 1205 and 1213 are retried up to 3 times. A repeated draft returns the existing code with replayed: true, and a draft of another user gets 409.
  4. Staff state changes send {from, state} and run UPDATE … SET state_id = ? WHERE order_no = ? AND state_id = ?; zero rows means a re-read and 409 with the current state, or 404. Plan decisions lock the order row with FOR UPDATE, check that the plan is still open, write the record and the state in one transaction, and send chat and alarms after commit.
  5. Each process has a 15-connection pool, a 5 s acquire timeout (a timer raced against getConnection, a late connection is released), a 1,000-entry wait line and max_execution_time of 30 s per session. A busy pool on /v1/* answers 503 with Retry-After: 2; legacy routes keep their old 500.

Why this way

The YYYYMMDD-NNN code is a business format, so a row lock per day prefix on the existing MySQL keeps the format, serializes only orders of the same prefix and works next to the legacy writer without a new service. Snowflake IDs were rejected because they change that format, and a Redis lock was rejected as unnecessary because a MySQL row lock plus a conditional UPDATE already give the guarantee.

Q&A

Q. The same draft is submitted twice at once (double click, retry after a timeout). What happens?
Both requests wait on the same day-prefix row lock; the second then finds the first order in submit_keys and returns the same code with replayed: true. If they still collide on insert, the 1062 handler re-reads and returns the existing code, so one draft creates at most one order.
Q. Where is the bottleneck when many doctors order at the same time?
The day-prefix row lock serializes order creation within one prefix; in the 500-doctor load test on one development PC it was the slowest point (order p95 6.8 s, list and detail p95 under 0.8 s). The lock covers only the inserts and a folder rename, and a folder that Windows holds open is copied after the transaction rolls back, so another doctor no longer waits 4.2 s (now 19–64 ms).

Steps

  1. Every AI entry point (the new-order draft run, the order run, the picked-series run and the legacy one-request routes) inserts an gpu_job row with status queued and a kind. One order can have only one waiting or running job; another request gets 409.
  2. A worker loop claims in one transaction: it locks a free gpu_slot row FOR UPDATE (no job, or an expired lease), then the oldest claimable job FOR UPDATE ordered by created_at, id. It sets running, adds an attempt and writes a new UUID lease_token and lease_until = NOW() + lease (DB clock) on both rows; a job past maxAttempts is marked failed instead.
  3. While the job runs, a heartbeat extends the lease with WHERE id = ? AND lease_token = ? AND status = 'running', and stage and finish updates use the same condition. If a worker dies, the lease runs out, another worker claims the job with a new token, and every write of the old attempt matches zero rows.
  4. A cancel (available for new-order draft runs) sets the job to cancelled under the draft row lock. The owning worker sees at its next heartbeat, or at once if the cancel came through the same process, that it no longer owns the job, aborts its AbortController, and the whole Python process tree is killed; a 45-minute watchdog does the same for runs that never end.
  5. Completion frees the slot, locks the draft, re-checks ownership and, if the draft was already submitted, locks the order; outputs move into the draft or order folder and only missing scans and order_files rows are inserted before the fenced succeeded update. A failure undoes the file moves, and order submission takes the same draft lock and merges results that finished earlier, so each result lands once.
  6. core-api picks finished, unannounced jobs and, under the job row lock, writes the order chat system message (idempotency key ai-<id>) and sets notified_at in one transaction. The bell and push follow after commit, so any number of core-api instances announce a job once.

Why this way

Jobs live in the MySQL that every service already shares, so a page reload, a dropped connection or a server change does not lose a run, and the slot rows bound GPU use however many worker processes exist. Redis/BullMQ was rejected because it is a new service that needs HA, and since MySQL 5.7 has no SKIP LOCKED, the claim locks a slot row first and then one job.

Q&A

Q. A worker process dies in the middle of a job. What happens?
Its heartbeat stops, so lease_until on the job and on its slot passes (default lease 120 s, heartbeat 30 s). The next claim sees the expired slot and the expired running job, issues a new token and counts the attempt; if the old process comes back, its updates carry the old token and change nothing, and after maxAttempts the job is marked failed with a message.
Q. How quickly does a cancel on another server free the GPU?
The cancel only changes the row, so the owning worker notices at its next heartbeat: about 1.7 s in the test with a 2 s heartbeat, and up to one interval with the default 30 s. A cancel through the same process is checked at once (the next job started within 50 ms in tests), and on the RTX A4500 the Python pipeline was killed in 0.3 s.

단계

  1. 주문 파일을 쓰거나 지울 때마다 경로당 한 행(경로 해시 UNIQUE)인 storage_outbox에 INSERT … ON DUPLICATE KEY UPDATE … version = version + 1로 upsert하므로, 같은 경로의 최신 작업이 이전 작업을 대체합니다. DB에 연결할 수 없으면 요청을 메모리에 보관했다가 복구되면 기록합니다.
  2. 프로세스마다 worker 루프 4개가 UPDATE … SET locked_by = <토큰> … ORDER BY id LIMIT 1로 처리할 행을 하나씩 점유하고 토큰으로 다시 읽습니다(MySQL 5.7에는 SKIP LOCKED가 없음). 15분이 지난 잠금은 빈 것으로 보므로 죽은 worker의 작업은 다시 처리됩니다.
  3. put은 파일의 SHA-1을 계산해 S3에 같은 크기와 sha1 메타데이터가 이미 있으면 건너뛰고, 아니면 업로드한 뒤(8MB 이상은 스트림) HEAD로 크기와 SHA-1을 확인합니다. 성공하면 WHERE id = ? AND version = ? 조건으로만 행을 지우고, 실패하면 10초에서 두 배씩 늘려 최대 1시간 백오프로 재시도하며, 로컬 파일이 사라졌으면 missing으로 보관합니다.
  4. S3 드라이버가 켜져 있으면 매일 밤 가장 최근 파일이 설정 일수(3일)보다 오래된 주문을 AI와 같은 주문별 잠금 아래에서 하나씩 정리합니다. DB에서 해당 회원의 실제 주문인 폴더만 대상으로 하고, draft와 테스트 계정은 건드리지 않습니다.
  5. 파일은 S3 목록에 같은 크기로 있고 바이트가 같다는 것이 증명될 때만 지웁니다: 단일 파트 ETag = 로컬 MD5, 아니면 sha1 메타데이터 = 로컬 SHA-1. 보류 폴더로 rename하고 크기 · mtime을 다시 확인한 뒤 삭제하며, 바뀐 파일은 하드 링크로 되돌리고 중단된 실행의 잔여 파일은 다음 시작 때 복원합니다.

파일은 사내 GPU 서버에서 만들어지지만 AWS에서도 써야 하고 네트워크 · 프로세스 장애에도 남아야 하므로, 모든 변경은 공유 MySQL의 영속 outbox를 거치고 로컬 사본 삭제에는 바이트가 같다는 증명이 필요합니다. 크기 · 시간만 비교하는 방식은 바이트를 증명하지 못해서, 모든 파일에 HEAD + SHA-1을 하는 방식은 레거시 업로드에 SHA-1이 없고 매일 밤 수십만 건의 요청이 생겨서 기각했으며, 목록에서 추가 비용 없이 오는 ETag를 먼저 씁니다.

Q&A

Q. 업로드가 진행 중인 파일이 다시 쓰이면 S3에는 어느 버전이 남습니까?
다시 쓰면 행의 version이 올라갑니다. 이전 업로드가 끝나도 정산 DELETE … WHERE id = ? AND version = ?가 0행이 되어 잠금만 풀리므로, 행이 다시 점유되어 새 내용이 업로드되고 검증됩니다.
Q. 레거시가 올린 multipart 파일은 SHA-1 메타데이터가 없고 ETag도 MD5가 아닙니다. 정리 작업은 이 파일을 어떻게 처리합니까?
증명에 실패하므로 파일은 디스크에 남고, 실행 결과에는 'S3와 같다고 증명되지 않음'으로 집계됩니다. 증명하지 못한 파일은 지우지 않으므로, 비용은 데이터가 아니라 디스크 공간입니다.

Steps

  1. Every write or delete of an order file upserts one storage_outbox row per path (unique hash of the path) with INSERT … ON DUPLICATE KEY UPDATE … version = version + 1, so the newest operation for a path replaces older ones. If the database cannot be reached, requests are held in memory and written when it returns.
  2. Four worker loops per process each claim one due row with UPDATE … SET locked_by = <token> … ORDER BY id LIMIT 1 and read it back by token, because MySQL 5.7 has no SKIP LOCKED. A lock older than 15 minutes counts as free, so the job of a dead worker is taken again.
  3. A put hashes the file with SHA-1, skips it when S3 already has the same size and sha1 metadata, and otherwise uploads it (streamed from 8 MB) and checks it with HEAD (size and SHA-1). Success deletes the row only WHERE id = ? AND version = ?; a failure retries with backoff from 10 s doubling to 1 h, and a vanished local file is parked as missing.
  4. Each night, when the S3 driver is on, orders whose newest file is older than the set number of days (3) are evicted one by one under the same per-order lock the AI uses. Only folders that are real orders of that member in the database are considered; drafts and test accounts are never touched.
  5. A file is removed only when S3 lists it with the same size and the bytes are proven equal: a single-part ETag equal to the local MD5, otherwise the sha1 metadata equal to the local SHA-1. It is renamed into a holding folder, checked again (size, mtime) and deleted; a changed file is put back with a hard link, and leftovers of an interrupted run are restored at the next start.
  6. Chat attachments go to S3 from any core-api server: each 8 MB chunk becomes a multipart part, and received_bytes advances only through a conditional UPDATE, so a repeated chunk counts once. Finalize locks the upload session row with FOR UPDATE, checks the part list and completes the multipart upload once.

Why this way

The files are made on the office GPU server but must be available on AWS and survive network and process failures, so every change goes through a durable outbox in the shared MySQL, and deleting the local copy requires proof of equal bytes. Checking only size and time was rejected because it does not prove the bytes, and HEAD plus SHA-1 for every file was rejected because legacy uploads lack SHA-1 and it would mean hundreds of thousands of requests a night, so the free ETag from the listing is used first.

Q&A

Q. A file is rewritten while its upload is still in flight. Which version ends up in S3?
The rewrite bumps the row's version. When the old upload finishes, its settle DELETE … WHERE id = ? AND version = ? matches nothing and only the lock is released, so the row is claimed again and the new content is uploaded and verified.
Q. Legacy multipart files have no SHA-1 metadata and their ETag is not an MD5. What does eviction do with them?
The proof fails, so the file stays on disk and the run counts it as not proven equal to S3. Eviction never deletes a file it cannot prove, so the cost is disk space, not data.

  2. Multi-step rules run in one transaction under SELECT … FOR UPDATE on the parent row. A chat send locks the conversation, inserts the message with last_seq + 1 and commits; UNIQUE(chat_id, seq) and UNIQUE(chat_id, sender_id, client_msg_id) make a retried send return the original row, and the socket event goes out only after commit.
  3. The GPU queue locks a free slot row, then the oldest job, and writes a new UUID lease_token with lease_until from the DB clock; heartbeats and results apply only WHERE id = ? AND lease_token = ?. The S3 outbox claims a row with one UPDATE … ORDER BY id LIMIT 1 that stamps a unique token and settles with WHERE id = ? AND version = ?, so a file rewritten during upload is uploaded again.
  4. Code that takes several locks follows one documented order (slot, draft, job, order), so two paths cannot wait on each other. Lock-wait timeout (1205) and deadlock (1213) are retried up to 3 times, and order creation also retries 1062 when the duplicate is not a replay of the same draft.
  5. List and detail ETags come from a cheap fingerprint query: COUNT, MAX(updated_at) and SUM(CRC32(CONCAT_WS(…))) over the shown columns, plus child-row counts. A matching If-None-Match gets 304 before the heavy query runs, and because the version is read from the DB, writes by the legacy app are seen too.
  6. Schema changes are numbered additive SQL files; the runner stores a SHA-256 of each file (CRLF-normalised) in schema_migrations, refuses edited files and needs ALLOW_REMOTE=1 for a non-local host. App accounts are DML-only, and pools are sized against max_connections 151: 50 per legacy app, 15 per platform instance with a 5 s wait that ends in 503 with Retry-After on /v1.

Why this way

The DB is shared with legacy writers and an external program, so the rules live where every writer meets them: constraints, row locks and conditional updates in MySQL. A Redis lock or a Redis/BullMQ queue was rejected because it adds a new service that needs HA and a second source of truth, and Snowflake IDs were rejected because they would change the YYYYMMDD-NNN order code format.

Q&A

Q. A GPU worker dies in the middle of a job. What happens to the job, and to anything the dead attempt writes later?
Its heartbeat stops, so lease_until passes and the next claim takes the job again with a new lease_token. A late write from the old attempt is fenced by WHERE id = ? AND lease_token = ? and changes 0 rows, and after maxAttempts the job is marked failed instead of looping.
Q. Two staff members change the same order's status at the same moment. Who wins, and what does the loser see?
Both send the status they saw, and the conditional UPDATE … AND state_id = ? matches for only one. The other gets 409 with the current status and its screen reloads; in the proof test, 10 parallel changes gave one 200 and nine 409.

Steps

  1. PM2 restart loops were split by cause and fixed in code: a throw inside the bcrypt callback became return done(error), the single createConnection became a pool, and empty query results got null checks. The deploy now stops the app before npm ci and starts it after install, so PM2 no longer restarts a process whose node_modules is being replaced.
  2. Production MySQL showed max_connections 151 and Max_used_connections 152 while the order app's pool allowed 1,000. Each legacy app now has a pool of 50, so 50 + 50 + 1 backup + about 5 admin connections stays near 106, and a full pool shows up as an app error instead of refused connections.
  3. Hand-copied wildcard certificates were replaced by Let's Encrypt certificates per service: on Linux, Certbot with webroot validation (an acme-challenge location, because iptables moves ports 80 and 443) and a deploy hook that reloads nginx. On the Windows gateway, win-acme runs from Task Scheduler with filesystem validation and a reload script, and every certificate renews 30 days before expiry.
  4. A server-side job runs mysqldump --single-transaction every day at 02:00 for the order DB and the planning DB, keeps the last 30 copies, and on error deletes the partial file and logs it. The shared S3 bucket has versioning, a lifecycle for non-current versions, and cleanup of delete markers and unfinished multipart uploads.
  5. For SEEANN OFFICE, a push to main runs the tests first; only then Buildx pushes :latest and :<sha> images to GHCR, and an SSH step runs docker compose pull and up -d under set -e and script_stop. This was added after an expired registry login once left the job green while the old containers kept running.
  6. In the platform APIs, SIGTERM first disconnects WebSockets, then drains the HTTP server and closes the DB pool and Redis, with a 10 s hard cap. Sessions, rate-limit counters and socket fan-out live in Redis and chat files in S3, and a test boots two core-api instances on one DB and one Redis to check that they agree.

Why this way

Each fix removes a measured cause (log groups, Max_used_connections, expiry dates) instead of raising limits or restart counts. Full blue-green (two stacks behind an nginx upstream switch) was considered and deferred, because today's real cost is a few seconds of 502 while a container is recreated; deploying a fixed image SHA with a one-command rollback is the planned next step.

Q&A

Q. If the database server itself is lost, do these backups save you?
Not fully. The daily dumps are kept on the DB host, so they cover bad writes and deletes for 30 days but not the loss of the host; uploaded files are covered separately by S3 versioning. The written next step is a daily off-host (S3) copy with one real restore test.
Q. Why not blue-green deploys for zero downtime?
It was considered and deferred: at this size the measured pain is a few seconds of 502 while Compose recreates a container, which does not justify running two stacks and an nginx upstream switch. The code side is already prepared (graceful drain, shared state in Redis and S3, a two-instance test), and the next step is deploying a fixed image SHA with a one-command rollback.

  4. 편집은 PATCH /orders/changes로 들어오고, 주문마다 별도의 interactive transaction에서 먼저 부모 orders 행에 SELECT ... FOR UPDATE를 겁니다. 현재 overlay를 읽어 사용자가 편집할 수 있는 필드만 반영하고, 바뀐 필드마다 edit_history 행(이전 값, 이후 값, 사용자 id, 고정된 username, 행 전체 스냅샷)을 추가한 뒤 overlay를 upsert하거나 삭제합니다.
  5. 레거시 주문 DB는 동기화만 별도 mysql2 풀과 keyset 페이지 SELECT로 읽습니다. 동기화는 mirror 테이블만, 사용자는 overlay만 쓰므로 둘이 같은 행에 쓰지 않습니다.

왜 이렇게 했나

투영 방식은 사용자가 이미 쓰던 엑셀형 Univer 시트를 유지하면서 값을 서버 권한 검사 뒤로 옮깁니다. 계획의 첫 안이었던 셀 단위 저장의 새 AG Grid 테이블 모듈은, 투영만으로 같은 서버 검사를 UI 재구축 없이 얻을 수 있어 보류했습니다.

Q&A

Q. 두 사용자가 같은 주문을 동시에 고치면 한쪽 수정이 사라질 수 있나요?
아닙니다. 두 번째 트랜잭션은 그 주문 행의 FOR UPDATE 잠금을 기다린 뒤, 첫 번째가 커밋한 overlay를 읽고 그 위에 자기 필드를 합칩니다. 바뀐 필드마다 이력 행이 따로 남습니다.
Q. 오래된 브라우저 탭이 주문 값이 들어 있는 스냅샷을 저장하면 무엇이 저장되나요?
투영 결과만 저장됩니다. saveDocument은 클라이언트가 무엇을 보내든 UPDATE 전에 stripSheetValues을 실행하고, 읽기와 복원도 같은 처리를 하므로 오래된 스냅샷이나 체크포인트도 주문 값을 내보내지 않습니다.

Steps

  1. On every save, read and version restore of the shared order workbook, the server runs stripSheetValues. It finds order columns by a field key stored in the header cell's metadata (or the default header text) and deletes the value and formula of every registered order column in order rows, cached formula results, the app's "edited" marker notes and the order sheet's filter.
  2. When a user opens the sheet, the browser fills the values from GET /orders. The API merges the user_edits overlay onto the mirror orders rows and runs filterRow, which removes every field the user's team may not read, along with the _edited/_edits traces that carry the original value.
  3. Access comes from resolveAccess, a pure function: MASTER gets every field, otherwise the team rule, then the column default, then a built-in fallback, with order-DB-owned fields capped at read and unknown fields set to none. ColumnPolicy loads role, team and active flag from the DB on each request, and the same result is used for lists, history, SSE events and writes.
  4. An edit arrives at PATCH /orders/changes, and each order runs in its own interactive transaction that first takes SELECT ... FOR UPDATE on the parent orders row. It reads the current overlay, applies only fields the user may edit, inserts one edit_history row per changed field (old value, new value, user id, frozen username, full row snapshot) and upserts or deletes the overlay.
  5. The legacy order DB is read only by the sync, through a separate mysql2 pool with keyset-paged SELECTs. The sync writes only the mirror table and users write only the overlay, so the two never write the same rows.

Why this way

The projection keeps the Excel-like Univer sheet users already had while moving the values behind a server-side permission check. The plan's first option, a new AG Grid table module with per-cell storage, was set aside because the projection gave the same server check without rebuilding the UI.

Q&A

Q. Two users edit the same order at the same moment. Can one edit be lost?
No. The second transaction waits on the FOR UPDATE lock on that order's row, then reads the overlay the first one committed and merges its own fields on top. Each changed field gets its own history row.
Q. An old browser tab saves a snapshot that still contains order values. What gets stored?
Only the projection. saveDocument runs stripSheetValues before the UPDATE whatever the client sent, and read and restore run it too, so old snapshots and old checkpoints never serve order values.

단계

  1. 주문 시트를 연 브라우저 탭마다 /events로 EventSource 하나를 열고, EventSource는 헤더를 보낼 수 없어 토큰은 쿼리 문자열로 보냅니다. 서버는 연결 수를 세어 0 → 1이면 동기화 타이머(기본 30초, 최소 5초)를 시작하고 1 → 0이면 멈추므로, 아무도 시트를 열지 않았을 때는 레거시 DB로 동기화 조회가 가지 않습니다.

왜 이렇게 했나

Q&A

Q. 배치를 보내는 중에 네트워크가 끊기면 편집이 사라지거나 두 번 저장되나요?
확정되지 않은 편집은 큐로 돌아가고, 같은 셀에 더 새로운 값이 있으면 그 값이 우선하며, 2/5/15/30초 후 다시 보냅니다. 각 항목은 목표 값을 담고 있고 서버는 값이 실제로 바뀔 때만 이력 행을 쓰므로 재전송해도 안전합니다.
Q. 백엔드 인스턴스를 두 개 띄우면 어떻게 되나요?
연결 수, 동기화 타이머, 진행 중 promise가 프로세스 메모리에 있으므로 인스턴스마다 자기 SSE 클라이언트만 세고, 각자 동기화 루프를 돌며, push도 자기 클라이언트에게만 보냅니다. 현재 배포는 백엔드 컨테이너 하나이고 이 설계는 그것을 전제로 합니다.

Steps

  1. Each browser tab with the order sheet open holds one EventSource to /events, with the token in the query string because EventSource cannot send headers. The server counts connections: 0 to 1 starts a sync timer (30 s by default, minimum 5 s) and 1 to 0 clears it, so no sync reads reach the legacy DB while nobody has the sheet open.
  2. A sync reads the legacy tables in keyset pages, compares 15 fields with the mirror, inserts new rows and updates changed ones, then pushes rows.changed; the status list goes only to users who may read both order_no and status. Concurrent callers await the same in-flight promise, and the first GET /orders after a long idle waits for a silent catch-up sync whose errors are logged, not returned.
  3. In the browser, SheetValueChanged covers typing, paste, fill, undo/redo, find-replace and AI writes. Each changed cell is compared with the value the DB will hold (queued, then in flight, then confirmed), and only differences are queued, debounced 400 ms and sent as up to 500 orders per PATCH /orders/changes.
  4. Failed requests are put back in the queue without overwriting newer values and retried after 2, 5, 15 and 30 s; a 403 is shown and not retried. A change touching more than 20 orders or 100 cells asks for confirmation, and declining undoes it.
  5. App writes, such as filling DB values on open or restoring a locked cell, run inside withAppWrites: it marks the top of the workbook's undo stack and pops every item recorded above the mark afterwards. Ctrl+Z therefore only reverts the user's own edits.
  6. The snapshot autosaves 2.5 s after the last mutation with the current rev; the server runs UPDATE ... WHERE id = ? AND rev = ?, 0 rows means 409, and the client then stops autosaving and offers a reload. A version checkpoint is written at most once per 10 minutes and only the newest 30 are kept.

Why this way

Gating the sync on live SSE connections replaces many browsers polling with one server loop and sends no sync reads to the shared legacy DB when nobody is working. The write-back compares each cell with the DB baseline instead of interpreting each Univer operation, so one event covers every edit path and the sync's own writes and full-row sorts produce nothing to send.

Q&A

Q. The network drops while a batch is in flight. Can edits be lost or written twice?
Unconfirmed edits go back into the queue, where a newer value for the same cell wins, and are resent after 2/5/15/30 s. A resend is safe because each item carries the target value and the server writes a history row only when the value actually changes.
Q. What happens if you run two backend instances?
The connection counter, sync timer and in-flight promise live in process memory, so each instance would count only its own SSE clients, run its own sync loop and push only to its own clients. The current deployment runs a single backend container, which this design assumes.

  2. 데이터 마이그레이션은 snapshot, plan, apply, rollback 명령을 가진 스크립트이며, snapshot은 READ ONLY 트랜잭션에서 PK와 값을 읽어 백업으로 저장하고 apply는 연결된 DB를 --target으로 정확히 적어야 실행됩니다. 모든 UPDATE ... WHERE pk = ? AND col = <스냅샷 값>을 한 트랜잭션에서 실행해 하나라도 0행이면 전체를 롤백하고, --dry-run은 항상 롤백합니다.
  3. 스키마 변경에는 drift가 있으면 migrate reset을 제안하는 prisma migrate dev를 쓰지 않습니다. migrate diff --script로 만든 SQL을 직접 검토해 db execute로 적용하고 migrate resolve --applied로 기록하며, 전후 행 수를 비교하고 릴리스 전에 mysqldump를 받습니다.
  4. AI는 서버가 도구 12개를 선언하고 모델 응답을 스트리밍하며, 브라우저가 각 tool_use를 Univer Facade로 실행해 변경을 일반 undo 스택에 넣고 tool_result를 돌려보내는 과정을 최대 8회 반복합니다. API 키가 없으면 503, 사용자별 일일 카운터를 넘으면 429를 반환하고, 문서 제목과 선택 범위는 JSON 문자열로 감싸 시스템 프롬프트에 넣습니다.
  5. 토큰 수명은 12시간이고, 절반이 지나면 보호된 응답마다 X-New-Token 헤더로 새 토큰을 줍니다. 매 요청에서 계정도 확인하므로(5초 캐시, 사용자 수정 시 즉시 삭제) 비활성화된 사용자는 401을 받고, 로그인은 없는 username이어도 더미 bcrypt 해시와 비교합니다.
  6. main에 push하면 CI가 단위 테스트, 이미지 빌드, GHCR에 latest와 커밋 SHA 태그로 push, SSH로 docker compose pull과 up -d를 set -e로 실행하므로, pull이 실패하면 job이 실패로 표시됩니다. Compose는 nginx(유일한 공개 포트), Next.js, NestJS를 30초 헬스 체크와 3 × 10MB 로그 순환으로 실행합니다.

왜 이렇게 했나

KST 규칙을 Prisma 확장 하나에 두어 나머지 코드는 실제 시각(instant)으로 동작하고 새 컬럼도 자동 포함되며, 이전 방식(DB 생성 KST 기본값과 UI의 +9시간 보정)은 같은 컬럼에 두 시간대를 섞고 스키마 drift를 일으켰습니다. 개발과 운영이 product DB 하나를 함께 쓰므로, 전체를 지울 수 있는 reset을 제안하는 migrate dev는 쓰지 않았습니다.

Q&A

Q. 스냅샷을 뜬 뒤 apply 전에 사용자가 행을 수정하면 어떻게 되나요?
그 행의 보호된 UPDATE가 0행에 해당하므로 스크립트가 트랜잭션 전체를 롤백하고 해당 행을 출력하며, 아무것도 쓰지 않습니다. 2026-10-08 운영 시간 변환에서 실제로 첫 적용이 변경 1건 때문에 거부됐고, 새 스냅샷 후 406개 값을 커밋했으며 이후 스냅샷에서 1,810개 값이 그대로인 것을 확인했습니다.
Q. KST 확장이 다루지 못하는 것은 무엇인가요?
raw SQL($queryRaw, $executeRaw)은 Prisma 쿼리 확장을 거치지 않으므로, raw SQL로 시간을 쓰지 않는 것이 규칙입니다. 백엔드의 raw 쿼리는 SELECT ... FOR UPDATE 행 잠금과 헬스 체크 SELECT 1뿐이고 둘 다 시간을 쓰지 않습니다.

Steps

  1. PrismaService returns this.$extends(tzExtension()), so every model query goes through one layer: Date values in writes and in where/cursor filters move +9 h, results (including relations and _min/_max) move -9 h, and missing @default(now())/@updatedAt values are filled with KST now. Timestamp fields come from the Prisma DMMF, and @db.Date business dates are skipped.
  2. Data migrations are scripts with snapshot, plan, apply and rollback: snapshot reads primary keys and values in a READ ONLY transaction and saves them as the backup, and apply refuses to run unless --target names the connected DB. All UPDATE ... WHERE pk = ? AND col = <snapshot value> statements run in one transaction; if any affects 0 rows, everything is rolled back, and --dry-run always rolls back.
  3. Schema changes skip prisma migrate dev, because on drift it offers migrate reset. The SQL comes from migrate diff --script, is reviewed by hand, applied with db execute and recorded with migrate resolve --applied, with row counts compared before and after and a mysqldump taken before the release.
  4. For AI, the server declares 12 tools and streams the model reply; the browser runs each tool_use through the Univer Facade, so the change lands in the normal undo stack, and sends a tool_result back, for at most 8 rounds. With no API key the endpoint returns 503, a per-user daily counter returns 429, and the document title and selection enter the system prompt as JSON-quoted strings.
  5. Tokens last 12 h, and once past half their life any protected response carries a fresh one in X-New-Token. Each request also checks the account (cached 5 s and cleared on user update), so a deactivated user gets 401, and login compares against a dummy bcrypt hash when the username does not exist.
  6. On push to main, CI runs unit tests, builds the image, pushes it to GHCR as latest and the commit SHA, and runs docker compose pull and up -d over SSH with set -e, so a failed pull turns the job red. Compose runs nginx (the only published port), Next.js and NestJS with 30 s healthchecks and 3 x 10 MB log rotation.

Why this way

The KST rule lives in one Prisma extension so the rest of the code works with real instants and new columns are covered automatically; the earlier approach, DB-generated KST defaults with +9 h fixes in the UI, mixed two time zones in the same columns and caused schema drift. migrate dev was rejected because development and production share one product DB, where a suggested reset would drop everything.

Q&A

Q. The migration snapshot is taken, then a user edits a row before apply. What happens?
That row's guarded UPDATE matches 0 rows, so the script rolls back the whole transaction, lists the row and writes nothing. In the 2026-10-08 production time conversion the first apply was refused for one changed row; after a new snapshot 406 values were committed, and a later snapshot showed 1,810 values unchanged.
Q. What does the KST extension not cover?
Raw SQL ($queryRaw, $executeRaw) bypasses Prisma's query extension, so the rule is that no timestamp is written through raw SQL. The only raw queries in the backend are the SELECT ... FOR UPDATE row lock and the health-check SELECT 1, and neither writes a time.
