보안 · 데이터 보호

Security and data protection

환자 CT와 주문 데이터를 다루기 때문에 보안은 기능이 아니라 기본값입니다. 세션은 서명된 쿠키 + Redis 저장소로, 권한은 토큰이 아니라 요청마다 DB에서 읽습니다. 오피스 플랫폼은 운영 DB에 읽기 전용으로만 붙고, 열 단위 권한과 추가만 되는 감사 이력을 둡니다. 로그인은 없는 계정도 bcrypt에 같은 시간이 걸리게 했고, rate limit은 사용자 단위로 Redis Lua로 공유하며, 위조된 X-Forwarded-For는 거부합니다. 레거시 서버 보안 점검에서 위험한 엔드포인트와 명령도 정리했습니다.

Because the data is patient CT scans and orders, security is the default, not a feature. Sessions use a signed cookie plus a Redis store; permissions are read from the DB on every request, not trusted from a token. The office platform connects to the production DB read-only, with column-level permissions and an append-only audit log. Login takes the same bcrypt time for unknown accounts, rate limits are per user and shared through Redis Lua, and forged X-Forwarded-For headers are rejected. A security review of the legacy servers also removed dangerous endpoints and commands.

session security · JWT (sliding renewal) · bcrypt · helmet · rate limiting · RBAC (column-level) · audit log · read-only DB access · S3 lifecycle · backups

MLOps and running AI models

I reduced the nnU-Net segmentation pipeline’s peak memory from 1.68 GiB to 122 MiB with mathematically identical output, and tested, benchmarked and deployed LLM models with Docker Compose in an air-gapped network.

DB와 세션: 서버가 몇 대여도 사용자는 한 번만 로그인합니다

Databases and sessions: however many servers, the user logs in once

레거시 서버는 요청마다 DB에 새 연결을 만들고 있었습니다(createConnection). 연결을 만드는 비용이 요청마다 들고, 요청이 몰리면 MySQL 연결 한도에 먼저 부딪혀 서버가 멈췄습니다. 8월 점검 때는 DB가 연결을 거부했습니다. 연결을 미리 만들어 두고 빌려 쓰는 커넥션 풀로 바꾸고, 풀 크기는 "크게"가 아니라 프로세스 수와 DB 한도를 보고 예산으로 정했습니다.

The legacy server opened a new DB connection for every request (createConnection). Each request paid the connection cost, and under load the MySQL connection limit was hit first and the server stalled; during the August maintenance the DB refused connections. I moved it to a connection pool, where connections are created once and borrowed, and sized the pool as a budget from the number of processes and the DB limit rather than just making it big.

결정Decision앱 서버는 상태를 갖지 않는다. 사용자가 누구인지는 Redis가, 사실은 DB가 안다.App servers hold no state. Redis knows who the user is; the DB holds the facts.

풀은 크기가 아니라 예산A pool is a budget, not a size
프로세스마다 풀 15개, 획득 대기 5초, 대기열 1,000. 풀이 꽉 차면 멈추는 대신 503과 Retry-After: 2를 돌려줍니다. 한 DB를 여러 앱이 같이 쓰므로 프로세스 수 × 풀 크기가 DB 한도 아래에 오도록 계산하고, 서버를 늘릴 때마다 다시 계산합니다.15 connections per process, a 5 s acquire wait and a queue of 1,000. When the pool is full the API answers 503 with Retry-After: 2 instead of hanging. Several apps share one DB, so processes × pool size must stay under the DB limit, and I recompute it whenever servers are added.

~/seeann/orders

의사 200명이 동시에 주문해도 주문번호는 하나씩

200 doctors ordering at once, one order number each

주문번호는 날짜별 시퀀스 행을 FOR UPDATE로 잠그고 서버가 발급합니다. 같은 요청이 두 번 와도 멱등 키로 한 번만 만들어지고, 상태 변경과 후속 작업은 한 트랜잭션 안에서 outbox로 기록합니다. 화면은 SSR prefetch로 첫 로드에 브라우저 API 호출이 없고, 목록은 ETag/304로 바뀐 것만 다시 받습니다.

Order numbers are issued by the server from a per-day sequence row locked FOR UPDATE. A repeated request creates the order only once thanks to an idempotency key, and state changes plus follow-up work are written in one transaction through an outbox. The screen prefetches on the server so a cold load makes zero browser API calls, and lists re-fetch only what changed via ETag/304.

문제마다 맞는 동시성 도구The right concurrency tool for each problem
경합 상태는 CAS, 다단계 불변식은 FOR UPDATE, outbox는 버전 정산, 큐는 fencing 토큰. MySQL 5.7에는 SKIP LOCKED가 없어서 UPDATE … LIMIT 1 + 토큰으로 점유합니다.CAS for races, FOR UPDATE for multi-step invariants, version reconciliation for the outbox, fencing tokens for queues. MySQL 5.7 has no SKIP LOCKED, so claims use UPDATE … LIMIT 1 plus a token.

GPU는 한 대, AI 요청은 여러 곳에서. 그리고 서버가 쓰러지면

One GPU, AI requests from everywhere. And when a server falls over

AI 분할 요청이 네 군데에서 동시에 GPU로 가서 메모리가 터지곤 했습니다. MySQL 위에 임대(lease)와 fencing 토큰을 쓰는 작업 큐를 만들어 한 번에 하나만 돌고, 죽은 워커의 작업은 다른 워커가 새 토큰으로 가져가며, 옛 프로세스가 살아나도 결과를 덮어쓰지 못합니다. 파이프라인은 할당 지점까지 추적해 청크로 나눴습니다.

AI segmentation requests used to hit the GPU from four places at once and blow the memory. I built a job queue on MySQL with leases and fencing tokens: one run at a time, a dead worker’s job is taken over with a fresh token, and a process that comes back late cannot overwrite the result. The pipeline itself was traced to one allocation and chunked.
